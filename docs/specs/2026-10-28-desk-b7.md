# Desk B7 and desk-mode R2 to R4: the plan for straw-boss-desk

Status: plan, not approved. Written 2026-10-28 against pi-straw-boss 0.46.0 (npm, tag `v0.46.0`, `main` at `5f17641`), which `spike/win/pins.json` pins.
Sources: `docs/specs/2026-10-25-design.md`; `docs/specs/2026-10-27-team-profile.md`; `spike/win/` (RUNBOOK.md, start.ps1, stop.ps1, lib.ps1, proto/); `spike/mac/`; pi-straw-boss `docs/specs/2026-10-26-sb-backend.md` (**Build steps** B7, **`gui.json` and its successor**, **Desk mode: what changes**, **`up`'s output**), `docs/specs/2026-10-26-desk-mode.md` (S1 to S10, **Rollout**, **Decisions**), `docs/how-it-works.md` and `src/server/cli.ts` at `v0.46.0`; VM reports `~/.local/share/sbd-review/kit-fix/report.md` and `~/.local/share/sbd-review/0.46.0-vm/report.md`.

## Intent

The shell needs one reliable way to start the stack, show the GUI, follow the GUI when its address changes, and stop the stack.
pi-straw-boss now runs a separate backend process, the sb server, that serves the GUI. Its B7 step adds the desk part: `cli.mjs up --dir --label` makes the shell's home base and its tower.
B7 waits for the pi-straw-boss release that carries B6 (the `towerRuns.enabled` flag default on).
This plan says what the shell and the kit do now on 0.46.0, what they do once B7 ships, which parts are pi-straw-boss changes (through that repo and its owner), and how each is accepted.

## Scope

- In: the start and stop order; how the shell gets the GUI URL and reloads it after a token rotation; the exit codes, `wait` values, and warnings the shell must handle; the kit and Electron prototype changes that work on 0.46.0; the pi-straw-boss changes B7 and desk-mode R2 to R4 still need, and who makes them; acceptance in the Windows VM (scripted) and on macOS.
- Out: editing pi-straw-boss or the design record (this plan only proposes changes to them); the phase 2 shell's wizard, bootstrap engine, and updater; the switchboard; Straw Link steps 6 to 8.

- **K3.** `/boss gui` and the 120 s wait for pi's painted UI only delay the URL now: `up` starts the GUI and prints its URL. The brief lists "one `/boss gui`" in the start order; this plan drops it (Q2).

- **K7.** The macOS kit pins pi-straw-boss 0.42.7 and pi-intercom 0.17.1. The sb server needs pi-intercom 0.18.1 or newer and exits 3 (`intercom`) without it. The kit has no `up` step, and its Electron app reads the top-level `gui.json`.

## Start order

The shell builds the environment itself (no inherited `PI_SUBAGENT_*`, `PI_INTERCOM_SESSION_ID`, `HERDR_PANE_ID`/`TAB_ID`/`WORKSPACE_ID`, `HERDR_SESSION`, `STRAW_BOSS_ROLE`). It sets `PI_CODING_AGENT_DIR`, the Herdr config and socket paths (Q1), and `STRAW_BOSS_DESK=1`. The same environment goes to `herdr server` and to every `cli.mjs` call.

### Now (0.46.0)

1. **Herdr.** Reuse a recorded `herdr server` only when its pid and start time match and `start.json` records the same environment fingerprint (`desk: true`, socket path). Otherwise start `herdr server` hidden, record its pid and start time, and wait until `herdr workspace list` answers (45 s).
2. **sb server and GUI.** `node <agent dir>/npm/node_modules/pi-straw-boss/dist/server/cli.mjs up --timeout 90 --exact`. Parse the last `{` line of stdout. Record `pid`, `started` (from the JSON; fall back to the process's own start time when it is absent), `log`, and the slot folder (`dirname(log)`). Handle the exit as **Exit codes** says.
3. **Show the GUI.** Print `GUI_URL=<url>` and `SB_DIR=<slot folder>`. The window loads `url` from `up`; nothing waits for a tower.
4. **Tower (stopgap until B7).** Keep `start.ps1` step 3 (wait for restored panes, reuse a restored tower, else `workspace create --env STRAW_BOSS_ROLE=tower` and `herdr agent start`). It runs after the URL is printed, so it delays nothing. A failure is logged and shown as a notice, not a failed start. No `/boss gui` is typed and no UI-paint wait runs. `-NoTower` skips the step.

Why the server comes before the tower: every pi Herdr starts then finds a live server and starts none of its own, and the URL does not wait for a pi start (58.9 s cold in the VM).

### After the B6 + B7 release

1. Herdr as above.
2. `cli.mjs up --dir <home base folder> --label <name> --timeout 120 --exact`. Its steps are `herdr`, `integration`, `version`, `server`, `base`, `tower`, `gui`. Record `workspace`, `pane`, `tower`, `created`, and `integration` too.
3. Show the GUI.

The kit then drops `start.ps1` step 3 (the tower stopgap), bootstrap's integration stage (`bootstrap.ps1:243`), and the restore wait. The home base folder is visible and under home (desk-mode spec, **Notes for the shell**), for example `~/Straw Boss`.

## Stop order

1. `cli.mjs stop`, with a 120 s limit on Windows and 45 s elsewhere (K6). It marks the server stopped on purpose, so a pi session's look does not start a new one while Herdr shuts down (VM 0.46.0 item 16b: a pi session restarted a killed server within about 0.1 s). It needs no running Herdr.
2. Wait until the recorded sb server pid with its start time is gone (10 s). If it is still there, kill it by pid only while the start time matches.
3. `herdr server stop`, then wait for its pid. Workspaces are not closed (Q3), so Herdr restores them at the next start.
4. Kill whatever of the recorded process tree still runs with its recorded start time. Kill the pi-intercom broker only when `broker.pid` in this agent dir names a node process that runs pi-intercom's broker (as now).
5. Leave `gui.json` and `server.json` alone: the server owns them, and `server.json`'s `gui.port` is how the next start keeps the port. Remove `start.json`.

The sb server goes first. If Herdr stopped first, a detached server would keep running for 60 s after Herdr went quiet, the panes' pi sessions could start a server again in between, and `herdr server stop` never reaches the server anyway (on Windows it is created through WMI, outside Herdr's tree).

On an Electron quit (phase 2): `before-quit` holds the quit (`preventDefault`), runs the stop sequence with its limits, then calls `app.exit`. If Electron crashes, the stack keeps running, and the next launch's step 1 reuses Herdr while `up` answers `server: "found"`.

## The GUI URL and a rotation

- **At start** the URL comes only from `up`'s `url`. The value comes from the server's own answer and already answers 200. The shell reads no file on the happy path (sb-backend spec, **`gui.json` and its successor**).
- **Afterwards** the shell watches the slot folder: `fs.watch` on the folder, plus a read every 2 s, since a watch on Windows can miss a rename. It reads `server.json` for `stopped`, `restarting`, `pid`, and `gui: {port, token, stopped}`. It falls back to `gui.json`'s `port`, `token`, and `stopped` when `server.json` has no `gui`. Both files are written by rename, so a read never sees half a file; a parse failure is retried at the next tick. Both hold secrets: the token (and in `server.json`, the control socket's `secret`), so neither is logged. Log lines replace the token with `<token>`, as the prototype already does.
- **The shell does not poll `cli.mjs status` on Windows.** Every call is a new process that spends one owner-gate PowerShell start (2 to 5 s; how-it-works, **The owner gate costs PowerShell starts**). `status` is for diagnostics and the settings page.
- **States** (how-it-works, **States for a shell**), as the shell acts on them:

| State | Seen as | Shell action |
|---|---|---|
| live | URL answers 200, record unchanged | nothing |
| moved | `gui.port` or `gui.token` differs from the loaded URL, no `stopped`, no fresh `restarting` | GET the new URL every 250 ms until 200 (30 s at most), then `loadURL` it; the old URL answers 403 from then on |
| restarting | `restarting.since` within 10 s | keep the window; show a small "restarting" banner in the shell; act on moved when it clears |
| gui stopped | `gui.stopped` | show a shell screen "the GUI was stopped" with a Start button, which runs `up` |
| server stopped | `server.json` `stopped` (someone ran `/boss server stop`) | the same screen; Start runs `up`, which clears `stopped` |
| gone | URL unanswered for 10 s and no fresh `restarting` | run `up` once (one at a time), then load its `url`; a failure shows the **Exit codes** screen |

On macOS a pi session usually restarts a crashed server within about 6 s, and the shell then sees moved. The 10 s gone rule covers the case where no pi runs.
The page's own "address replaced" note is the fallback when the shell misses a change: it means the token moved, and the shell's next tick reloads.

## Exit codes, `wait` values, and warnings

From `src/server/cli.ts` and `client.ts` at `v0.46.0`. On failure, `up` writes one JSON line on stderr: `{step, wait?, reason, steps, warnings, log, startError?}`. `stop` writes plain text.

### `up`

| Exit | Meaning | Shell action |
|---|---|---|
| 0 | done; `server` is `found`, `started`, `restarted`, or `upgraded` | load `url`; handle `warnings` (below) |
| 1, `wait: "lock"` | `server.lock` was held by another start or restart for the whole time | run `up` once more; a second failure is shown with `reason` |
| 1, `wait: "start"` | this `up` started the server and it did not answer `hello` (60 s on Windows), or the GUI URL did not answer in time | show `reason`, `startError` when present, and the log's tail (`cli.mjs logs --lines 40`); offer Retry |
| 1, `wait: "hello"` | another requester's start was under way and no `hello` came | run `up` once more |
| 1, `wait: "exit"` | the old server did not leave for a restart (an upgrade or the desk switch) | run `up` once more; then show `cli.mjs status` |
| 1, step `herdr` | no Herdr answers, or the record serves another socket (a copied state folder) | restart the Herdr step once; a socket mismatch is a broken install and is shown |
| 1, step `version` | only with `--exact`: the running server is newer than the pin | run `cli.mjs restart --downgrade --reason "stack.json pin"`, then `up` again (the pin is the shell's decision) |
| 1, step `server` | a refusal (another broker scope or transport) or no start | show `reason` |
| 1, step `gui` | the GUI did not start (`lastError` and 20 log lines are in `reason`) | show it; offer Retry |
| 2 | usage; after B7 also `--dir` without the switch | a shell bug: log and fail fast |
| 3 | the server cannot run: `startError.code` `loader` (`tsx` missing), `intercom` (pi-intercom older than 0.18.1), or `acl` (the Windows state folder could not be protected or belongs to another account) | `loader` and `intercom`: run the bootstrap's pi-packages repair; `acl`: show `startError.text`, which says what to do |

| Warning | Shell action |
|---|---|
| `server_newer` | not seen with `--exact` |
| `desk_on` | never expected (the shell always sets the switch): log it as an environment bug |
| `breakaway_failed` | Windows: the server ends with its starter's job; show a diagnostics notice, keep running |
| `server_unreachable` | an elevated server runs; tell the person to quit the elevated pi or shell; the GUI may still load from the recorded URL |
| `remote_off` | log only (remote access is hidden in desk mode, S9) |
| `integration_installed` (B7) | log only |

### `stop`

| Exit | Meaning | Shell action |
|---|---|---|
| 0 | `{"outcome":"stopped"}` or `{"outcome":"already-down"}` | go on |
| 1 | text: a busy lock past its wait, `unreachable` (elevated server, or no answer to the stop), `scope` (another broker scope), `exit-timeout` (asked, did not exit) | go on to step 2 (kill by recorded pid and start time); `unreachable` from an elevated server cannot be killed either and is reported |
| 3 | `acl` | report; go on with Herdr |
| 5 | a `serve` server (a supervisor's) | never expected for the desk: report, do not kill |

### `status`

Exit 0 with one JSON line: `state`, `primary`, `url`, `log`, and the record's facts. Exit 3 on `acl`, 1 on another failure.

## Risks

- **Pane environment on Windows (Q1, K2).** Herdr rebuilds a Windows pane's `PATH` from the registry (spike finding; the team-profile spec, **Isolation**, says its environment). If a pane's pi does not get `XDG_CONFIG_HOME` or `STRAW_BOSS_DESK`, it computes another slot than the server's (the same socket judged secondary) and starts a second server, or treats the stack as normal mode. Task 1's acceptance reads the variables from inside a pane. If they are dropped, the fallback is a `tools/bin` launcher for pi that sets them, as the team-profile spec does for `gh` and `glab`, and the finding goes to Herdr.
- **The primary slot (Q1)** relies on `XDG_CONFIG_HOME` being read by nothing else in the stack in a harmful way. Git reads `$XDG_CONFIG_HOME/git/config`, but `GIT_CONFIG_GLOBAL` already overrides the global file, and the folder is the app's own. `gh` and `glab` take their own config variables first (team-profile spec, **Isolation**). This is checked once in the VM (task 6).
- **Keeping workspaces (Q3)** brings back whatever the PM left open, including resident towers of 0.46.0. Start step 4's restore wait handles one tower; a stray duplicate is still closed only when it holds nothing else, as now.
- **Killing the broker at stop** drops mail kept for tower identities while the server is down. That mail matters only once the tower service runs (B5 and later); revisit then.
- **`cli.mjs status` cost on Windows** (one PowerShell start each): the shell never polls it; only the settings page and diagnostics call it.
